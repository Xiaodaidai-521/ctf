## 值得保留的设计

1. 区分敏感性、异常、违规、决策、执行授权与实际交付；不把异常模型输出直接当违规概率。
2. 输入准备、纯判断核心、生产决策三层分离；明确越权先拒绝，不允许低风险分数抵消权限限制。
3. 不复用法律关键词评分作为联合研判，也不把学习行为当安全基线、下载点击数当交付量。相关源码支持这些判断。
4. 请求、预占和交付分开计量；配额只有一个权威维护方；明确并发测试需要真实数据库锁语义。
5. 合成数据与真实效果分开陈述；四组对照、消融、按时间和实体隔离、带状态回放以及失败不移出分母的原则正确。
6. 合成 Provider 可以支持前期开发；主线一契约、授权源及生产 owner 未明确时，不宣称已完成真实接入。

## 分级问题

### R1 [P1] 执行授权缺少领取、消费与终态契约

**位置：**方案 §6.6（196–200 行）、§7（231–243 行）；任务规格 H4–H6（850–910 行）。

方案用「保存 authorization_id、同键重新复核」解决重复签发问题，这个方向合理。但同一个授权 ID 并不自动意味着只能交付一次。目前没有约定谁负责原子领取授权、何时算消费、执行失败后是否可以重试，以及过期、撤销、已消费状态能否重新变成 executable。

**触发条件：**两个执行工作进程同时持有同一个有效授权，分别通过当前权限检查并启动交付；或者旧幂等键在第一次交付已完成后再次请求执行。只返回同一 ID、重新检查权限与额度，都不能单独排除再次交付。

另一个未定义的分支是：同一 request_fingerprint 和幂等键，传入不同 decision_id 或执行计划。方案只描述 fingerprint 冲突，未说明政策变化后旧授权是否会被复用于新决定。

**应补：**

- 明确幂等键的作用域及绑定对象：可信主体/组织/环境、操作、请求修订与摘要、决定、计划和义务摘要；不应把这些全部留给调用方自行解释。
- 定义授权的有效、领取中、已消费、过期和撤销等状态，以及允许的状态转换。原授权终态不得因重新授权而复活；需要重评时关联一个新版本。
- 与执行支线共同定义原子 `claim/consume` 或等价端口、单次执行标识及消费方职责。主线二无需实现文件交付，但必须给出接入契约。
- 对开始执行后结果未知的请求，先核对执行结果，不盲目再次交付；不把数据库事务表述成跨网络交付的天然 exactly-once。

**验收反例：**同授权双消费者只有一个能领取；已消费授权重放不会再交付；同键更换决定/计划有确定响应；撤权后恢复权限不会复活旧授权；两次共享访问需要按约定分别授权或受明确次数约束。

### R2 [P1] 配额只有端口名称，缺少共同锁定对象及恢复规则

**位置：**方案 §3 第三项（92 行）、§6.4（176–185 行）、§8（262–264 行）；任务规格 H6（899–910 行）。

`reserve/commit/release/reconcile`、事务、行锁、期限都是必要方向，但目前还没有可实施的配额契约：额度按哪个主体、数据域、接收者、窗口与单位汇总，多个预占锁定哪个共同资源，实际交付如何结算，均未明确。

**触发条件一：**剩余额度 100，两条不同请求各预占 60。如果只分别锁自己的 QuotaReservation 行，两边都可能看到足够余额。锁预占记录不等于锁定共同额度，首次创建额度桶也需要处理竞争。

**触发条件二：**已预占 100、实际可能交付 60，执行回执丢失后预占到期。如果到期直接 release 100，新的请求可以再次占用原本已消耗的额度。方案列了部分交付/未知结果测试，但没有给出其预期状态。

**应补：**

- 定义配额键、计量单位和窗口口径；确定共同额度桶/账户锁或等价的数据库原子更新策略，以及首次创建、多个额度桶的锁顺序。
- 明确已结算量、有效占用量和结果未知占用量如何计入限制，避免重复计算或提前释放。
- 给出状态转换表及端口的参数、幂等键、返回值、冲突与恢复语义；未知结果不得仅因 TTL 到期被视为未交付。
- 明确授权有效期与预占有效期的关系；启动执行时如何确认预占仍有效、如何阻止旧执行者在额度释放后继续交付。
- 同库实现说明本地原子边界；未来跨服务移交说明恢复与核对责任，不声称全局原子。

**验收反例：**100 额度并发 60+60；空额度桶的首次并发创建；跨窗口边界；领取与到期释放竞争；部分交付后回执丢失；重复结算。行锁相关用例使用真实 PG 的独立连接与受控交错。

### R3 [P1] 模拟输入隔离仍是声明，缺少签发入口的可信来源准入契约

**位置：**方案 §3（92 行）、§6.4（182–185 行）、§7（215–234 行）、§10（308–312 行）。任务规格 B4、D4、H1、M 已明确禁止用模拟结果取得生产权限。

方案的 `is_simulated` 目前具体落在交付遥测上；其他输入只有来源/环境等概念，尚未定义生产决策入口如何识别并拒绝合成授权、模拟审批、模拟配额或评估快照。标注「非生产权威」不能替代实际准入条件。

**触发条件：**生产入口被错误装配了返回 authorized 的合成 AuthorizationProvider，或者评估生成的 assessment/decision 被拿来调用 prepare_execution。若入口只检查字段完整、权限值和有效期，模拟对象也可能通过。

**应补：**

- 建立各 Provider 的权威身份、来源模式、环境、作用域和版本契约；这些信息由可信注册/装配层确定，不能信任客户端传入的 `is_simulated=false`。
- 生产签发只接受已配置的生产权威源及服务端读取的决定；评估环境不能访问生产签发与生产配额写端口。
- 对生产配置中出现测试适配器、生产 owner 缺失或依赖不可用给出明确拒绝/降级结果，不回退到内存适配器。

**验收反例：**模拟授权接生产入口、跨环境重放决定、伪造环境字段、缺失 owner、评估参数调用签发。验收重点是没有授权与生产配额写入，而不只是返回了警告字段。

### R4 [P2] 对照实验遗漏共同基础保护，预注册口径尚不完整

**位置：**方案 §6.2（160–167 行）、§9（284–300 行）；任务规格 I4 第 991–992 行及 I6–I7。

任务规格要求所有组执行相同的「硬性权限与基础保护要求」，方案却只明确共享硬约束，把敏感画像主要放进 D 组，并提出按 tag 去除敏感输入。如果 A/B/C 或消融组连强制脱敏等基础义务都被去掉，D 的优势可能只是多实现了必需的安全政策，无法归因于联合研判。

**应补：**把共同权限检查与基础保护下限固定为不可消融层；说明 A/B/C/D 各自变化的特征、基线、模型、阈值和融合层。各组在权限与必需保护相同的前提下比较额外分析价值，测试中验证共同义务不受分组影响。

预注册的 H1–H4 目前仍是定性假设：

- A 永不限制时，「首次限制位置」如何计数或作为删失结果报告？
- H2 的「不劣于」是描述性比较，还是有预先指定容忍差与不确定性估计的统计结论？
- deny、defer、require_approval、mask 各自如何计入误拦、延迟和业务代价？
- 「更强义务」如何比较？脱敏、限制有效期和增加审批并不自然构成单一强弱顺序。

应预先写清分析单位、分母、重复种子/序列、数据切分、指标公式和失败处理。没有已批准的效果或性能目标，可以报告基线和实测值，但不能在实验后再定义达标线，也不能直接声称统计不劣。

### R5 [P2] Stage 2 缺少可冻结的具体设计表，批准状态也不自洽

**位置：**方案 §5–§7、§10、§11（318–319 行）、HANDOFF（431–433 行）；任务规格 Stage 2 输出（603–615 行）。

目前的特征注册表、基线和政策表主要描述「将来怎么实现」，尚未给出 Stage 2 要求的实际 `feature_catalog`、`baseline_plan`、`decision_table` 与验收对应关系。只有 Stage 1 HANDOFF，JSON 格式正确，但不是 Stage 2 的交接内容。

**影响：**实现人员仍需在 M1–M4 自行决定窗口边界、去重口径、样本不足时的基线回退、缺失画像与未知权限的动作、审批与 mask 的组合方式、政策冲突优先级、错误码及版本兼容。接口名字已经固定，语义却可能在各适配器中分化。

**应补的最小附件：**

1. 服务所有权表：请求、资产版本、画像、权限、审批、配额、执行与事件各有明确生产者、消费者、权威源和缺失行为。
2. 首期特征表：从少量可验证特征开始，逐项落实任务规格 E4 的 11 项元数据，包括主体/数据域，区分静态定义与每次快照的动态水位。
3. 基线回退表：本人→群体→明确降级；给出候选最小样本与适用条件、历史截止点、污染处理，尚未批准的参数标为草案。
4. 决策表：输入质量、硬约束、业务授权、异常结果、敏感性如何产生 action、组合 obligations 与 reason_codes；义务不支持时的结果必须确定。
5. 字段契约与示例：类型、必填/可空、枚举、scope 和 fingerprint 的规范化方式、版本拒绝规则及至少一对请求/响应样例。
6. Stage 2 HANDOFF：已冻结内容、待批准内容、仅原型可继续的范围，以及与测试用例的映射。

**批准状态需统一：**方案 §11 把 M1 的 INSTALLED_APPS 两行列为允许修改，HANDOFF 却把同一项列为 authorization_remaining。单凭当前两份材料无法确认其他会话中的批准事实；应补批准来源/范围，或统一标记待批准，不能凭标题「已批准」推定迁移和生产配置均已授权。

OQ 的「不阻塞」应限定为不阻塞合成原型：主线一字段、正式公共契约与生产 owner 的缺失，仍会阻塞相应公共接口冻结或生产接入。任务规格 B3 的 acceptance_targets/resource_budget/data_policy 等输入也应记录已知值或 Unknown，不默认为已解决。

### R6 [P2] 审计复用未交代完整性边界和 outbox 重试去重

**位置：**方案能力清单第 55 行、§6.5–§6.6；源码 `backend/audit/services.py:57`、`:85`、`:127` 及 `backend/audit/models.py:100`。

「串行追加哈希链」的源码依据成立；称为完整的防篡改设施则过强。当前 `compute_entry_hash` 不覆盖 created_at；`verify_chain` 从现存第一条遍历到现存最后一条，没有独立的预期链尾/条数证据。纯内存验证结果：修改时间戳后校验仍通过，删除链尾后校验仍通过。

另外，append_entry 没有业务 event_id 的去重约束。同一个事件 payload 追加两次会得到两条记录。current_hash 唯一不等于事件唯一，因为 previous_hash 会变化。若 outbox 在台账追加已提交后、标记发送成功前崩溃，普通重试会重复记账。

**应补：**

- 将复用能力表述为「现存记录的哈希链一致性校验」，写明可证明与不可证明的范围。更强的防删除/防重写保证属于另行设计，不必为了本主线重构 audit。
- 对本地同库台账，规定 outbox 行领取、台账追加、完成标记处于同一事务，或采用明确的 event_id 去重方案；外部消费者仍自行处理至少一次投递。
- 明确事件时间、因果引用、敏感字段最小化与可见范围；重要事件时间可以纳入受哈希保护的 payload，不能默认台账 created_at 已被哈希绑定。

**验收反例：**追加与完成标记之间故障；多个消费者竞争同一 outbox 行；相同 event_id 重投。台账限制应在文档中保留，不因一个链校验返回 true 就宣称事件历史完整。

### R7 [P2] frozen dataclass 与 AST 黑名单不足以兑现不可变和纯度保证

**位置：**方案第 20 行、§4（118–119 行）、§6.1、§7；任务规格 E1/H1/H5。

`frozen=True` 限制字段赋值，但不会递归冻结 features 字典、obligations 列表或参数中的嵌套对象。纯 Python 验证中，构造 frozen dataclass 后修改原字典，快照值会随之改变。若 hash/decision 已生成，此后数据变化会破坏回放依据。

`assertNumQueries(0)` 与 AST 检查能捕获部分违规，但不能证明所有依赖无副作用：别名调用、间接函数、文件读取、网络、时钟和可变全局状态仍需约束。更实际的接口缺口是 assess_risk 仅接收 model_version/policy_version，尚未约定实际模型工件、预处理配置及政策内容由谁加载并保证固定。

**应补：**

- 在边界复制并递归规范化快照，使用不可变集合或不可变序列化载荷；验证摘要对应实际输入内容。
- 输入准备层解析并校验模型/政策工件，再显式提供固定的推理依赖或内容寻址句柄；说明版本、哈希、预处理和特征顺序的绑定，回放期间不能偷换为 latest。
- 把 AST 与零查询检查称为工程护栏；增加嵌套输入篡改、间接时钟/I/O、同输入重放、模型缺失及版本不匹配测试。

### R8 [P2] 「migrate app zero 即完全回滚」没有数据保留边界

**位置：**方案第 90、144、323–326 行；任务规格 L（1185–1190 行）。

迁移可反向执行不等于业务状态可以无损回滚。M1+ 若已有预占、授权、执行回执或决定，删除表会丢失未结算额度和追溯依据；已有审计链事件也不会因为删掉两个 app 自动消失。

**应补：**区分空库原型撤销与已产生业务状态的降级。前者可在确认无待保留数据、迁移依赖允许时反向迁移；后者先停止签发/写入、核对在途执行、保留账本与事件引用，再按批准的数据保留方案恢复代码或前向修复。文档不应把 migrate zero 作为通用生产回滚步骤。
