# 主线一：分阶段实施与验证提示词

本文件将完整提示词拆成 10 个可独立发送的执行段落。原始六阶段对应：第 1、2 步为核查与设计，第 3 步为底座，第 4—8 步为原 Stage 4，第 9 步为集成实验，第 10 步为交付。

## 使用方式

1. 在同一项目中按顺序发送各步骤代码块，每次只发送一个。
2. 每一步先实现本步内容、完成本步必要验证，再提交交接；不要一次执行全部步骤。
3. 每个代码块均引用完整提示词，因此换聊天后仍可使用。请确保执行者能读取引用文件；无法读取时应提供该文件，不能凭记忆重建约束。
4. “进入下一步”不代表批准此前未授权的公共契约、依赖、数据库执行或原文外发。已有明确批准也不必重新申请。
5. 某一步部分阻塞时，可以继续它的独立部分；后续步骤只消费已验证且满足前置条件的产物。用户发送下一步是启动信号，不是验收通过的证据。
6. 每步结束等待下一条用户指令，不自动推进。这是逐步执行模式对完整提示词末尾“持续推进”的限定。
7. 本文件只是任务提示词；生成本文件不代表已执行任何开发阶段。

## 共同交接约定

执行者在 `docs/mainline1/` 下维护：
- `HANDOFF.md`：当前状态、批准记录、证据索引、阻塞项及下一步条件。
- `step-NN.md`：本步结果、修改、验证命令和实际结果；重要判断变化追加记录。
- 设计阶段生成的契约和验收文档，以及后续实验结果。

若仓库已有正式交接目录，先复用并在 HANDOFF 中记录实际位置。
文件路径、文档名和内部模块名可以适配仓库；跨模块契约语义不得自行改变。
交接只保存最小必要信息，不能包含凭据或敏感原文。

每步交接至少含：
```text
step / status: complete | partial | blocked
mission: 本步已解决 / 未解决
artifacts: 文件及作用
findings: 结论、证据位置、证据状态、置信度
changes: 动机、范围、依赖、重要替代方案、未验证假设、回滚
verification: 检查、命令、范围、Passed / Failed / Untested / Blocked、证据
approved_decisions: 批准内容与来源；未批准事项不能混入
judgment_changes: 原结论、新结论、新证据、影响
open_questions: 未知项、阻塞范围、所需决定
next_step_constraints: 下一步必需输入及禁止事项
```

能力状态、证据状态、置信度与测试状态沿用完整提示词，彼此独立。
没有执行的测试不得写成通过；Mock、规则路径与真实语义路径分别记录。
